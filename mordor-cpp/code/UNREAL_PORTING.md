# Moving the Mordor rules core into Unreal Engine

This C++ project was written so the rules can move into an Unreal module without being rewritten. This note says how the code is layered, what has to be replaced on the Unreal side, and how to check that nothing platform-specific has crept into the core.

## Layers

| Layer | Folder | Depends on | Unreal equivalent |
|---|---|---|---|
| Foundation | `include/mordor/types.h`, `math_util.h`, `rng.h`, `events.h`, `ctx.h` | the C++ standard library only | keep as is, or retarget the aliases (below) |
| Data tables | `include/mordor/game_data.h` (generated by `tools/gen_data.py`), `src/game_data_json.cpp`, `json_lite.*` | foundation | fill `GameData` from DataTables or JSON assets; drop `json_lite` and the loader |
| State | `include/mordor/state_*.h` | foundation | plain structs; wrap in one `UGameInstanceSubsystem`, never in UObjects |
| Rules | `include/mordor/<module>.h`, `src/<module>*.cpp` (68 modules, one per SRD part) | foundation, state | compile as an Unreal module, unchanged |
| Game layer | `include/mordor/game.h`, `src/game_*.cpp` | rules | the single API a front end calls |
| Front ends | `apps/console` | game layer only | Unreal UI, Slate/UMG widgets, input |

The rules never print, read files, read the clock, call `rand()`, or hold global state. Everything comes in through `Ctx` (data tables, random source, event sink) and everything goes out through return values, state changes and events.

## What to replace in Unreal

1. **Random numbers.** Implement `IRng` (`nextU32`, `nextDouble`) on top of `FRandomStream`. `Rng` (xoshiro128**) can stay for tests and replays.
2. **Events.** Implement `IEventSink::emit` to broadcast a delegate. Each `Event` has a stable `code` (for example `combat.hit`, `town.rest`, `dungeon.encounter`), optional English `text`, and numeric and string arguments. Drive sound, animation and the combat log from `code`; use `text` only for a quick prototype.
3. **Time.** The rules take milliseconds explicitly. Call `advanceTime(session, DeltaSeconds * 1000)` from the tick; the combat round (1000 ms), play clock (250 ms) and ailment tick (4000 ms) are driven from there. Nothing in the core sleeps or reads a timer.
4. **Data.** `GameData` is plain vectors of plain structs with the data file's field names. Import `data/combat-data.json` into DataTables and build `GameData` from them, or keep the small JSON reader.
5. **Strings and containers.** `types.h` is the only place that names `std::string`, `std::vector` and `std::array` (`Str`, `Vec`, `Arr`). Conversion to `FString` and `TArray` belongs at the boundary (the game layer returns `Str` for descriptions).
6. **Save and load.** `saveSession` and `loadSession` produce and read a line-based text. Store that text in a `USaveGame` string field.

## Unreal module settings

- `PublicIncludePaths` = `include/`; sources under `src/`.
- `bEnableExceptions = false`, `bUseRTTI = false`, C++17 (`CppStandard = CppStandardVersion.Cpp17`). The core is built with `-fno-exceptions -fno-rtti` here, so it already complies.
- Avoid clashes with Unreal macros and names: the core avoids `check`, `ensure`, `TEXT`, `PI`, `UCLASS`. Headers use `#pragma once` or include guards, and everything is inside `namespace mordor`.
- The core allocates only through standard containers; no `new`/`delete`, no `shared_ptr`, no threads.

## Portability check

`python3 -I tools/lint_portability.py` scans `include/` and `src/` for platform headers, C runtime calls, exceptions, RTTI, thread-local and file-scope mutable statics. It reports 0 violations at the time of writing (see `logs/lint.txt`). Run it after every change to the core.

## Known limits (be honest with the port)

- Many modules overlap because they were written from overlapping parts of the same specification. The game layer calls one routine per action; the others remain available but are not all exercised. `logs/` and `NOTES.md` list the overlaps found.
- The console demo is a rules harness, not a game design: no art, sound or real-time presentation. The combat clock runs per command.
- Some behaviours the specification marks UNKNOWN or CONFLICT were chosen by the implementing worker; search for `UNKNOWN:`, `CONFLICT:`, `SIMPLIFIED:` and `ASSUMED:` in `src/` to find them.


## Feature registry and what is left for an engine port (2026-11-12)
- Commands are data: `registerFeatureCommand({verb, screen, handler, help})` in `src/features.cpp`; one file per feature (`src/feat_<id>.cpp`); `registerAllFeatures()` is generated by `tools/phase_features.py` (lines marked `FEATURE_DECLS` / `FEATURE_CALLS`). In Unreal the same table can drive widgets or Blueprint-callable nodes: the handler signature is `bool(Session&, const Vec<Str>& words, Str& reply)` with no I/O.
- State a feature needs beyond the rules core goes in `Session::featureState` (`std::map<Str,Str>`, text values). Hall records, buffer standing orders and rescue records live there. It is NOT yet saved (see CODING_REPORT.md).
- `include/mordor/access.h` is the single place that says how to reach party members, packs, gold, companions, spells, monsters, items and the square under the party. A port can re-point those helpers at engine objects.
- 527 translated rule functions are not reached by play or tests (`UNWIRED.md`); wire them as Blueprint events (spell effects, item effects, trap effects) rather than deleting them.
