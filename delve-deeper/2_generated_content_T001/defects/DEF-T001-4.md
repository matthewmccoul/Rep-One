# quest_transition_table compares the transition table with itself (EQV-13, EQV-14)

Spec: EQV-13 (C++ transitions equal the QJ `transitions` table) and EQV-14 (B) (an extra `not_offered --report--> completed` row makes EQV-13 fail).

Repro (mutation build, EXECUTED):
- fixture `work/T001/qa/fixtures/q_extra_transition.json` = real quest JSON plus one row `{from: not_offered, event: report, to: completed}`
- QA copy of `work/T001/code` in `work/T001/qa/mut/qst_extra_row` with `tests/quest/test_quest.cpp` `questPath()` pointing at that fixture; built in `work/T001/qa/build_mut/qst_extra_row`
- `python3 -I work/T001/qa/run_check.py EQV-14 -- ctest --test-dir work/T001/qa/build_mut/qst_extra_row --output-on-failure -R quest_transition_table --output-log work/T001/qa/out/EQV-14-ctest.log`

Expected: non-zero exit (test Failed).
Actual: exit 0, `qst_quest_transition_table Passed`. Cause (static): `QuestData::next` is filled from the same table the test reads (test_quest.cpp lines 819-840), so the comparison is circular. Also `Engine::report` handles `not_offered`/`declined`/`active`/`completed` in a hard-coded switch (quest.cpp ~lines 650-664) and never consults the table for them, so the extra row has no effect on behaviour and nothing compares behaviour with the table for those states.

Partial cover: `quest_check validate` on the mutated JSON rejects it with `FAIL STATE_TABLE not_offered + report gives completed, want not_offered` (work/T001/qa/out/EQV-14b.log, exit 1), so a bad table is caught at load, not by this test. EQV-13 as written still cannot fail on a table change.

Fix idea (SE's choice): make the test drive `Engine` (offer/accept/decline/arrive/report) through every (state,event) pair and compare the resulting state with the table; then the extra row must show as a disagreement.
