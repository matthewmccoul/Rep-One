## 0. Conventions (read first)
- Line form: `id | what it checks | command | input | expected exit code and output`.
- **CLI contract (PROPOSAL for the Software Engineer; if changed, record each change and reason).** After `cmake --build work/T001/build`, these executables exist in `work/T001/build/`: `com_check`, `map_check`, `puzzle_check`, `quest_check`, `eqv_check`. Exit 0 = accepted/pass, exit 1 = input rejected (validation failure), exit 2 = usage or I/O error. On rejection the program prints one line `FAIL <CODE>: <detail>` to stdout or stderr. Codes used below are QA's expected names; any equivalent code is fine if stable and documented, but the line must start with `FAIL`.
  - `com_check json <file>` / `com_check csv <file>`
  - `map_check validate <map.json>`; `map_check neighbours <map.json> <node>`; `map_check door <map.json> <edge>`; `map_check ways <map.json> <edge>`; `map_check reach <map.json> <from> <to> [blocked_edge ...]` (prints `reachable` or `unreachable`; the graph is undirected, doors pass both ways, as in validate_map.py).
  - `puzzle_check validate <puzzle.json> <map.json>`; `puzzle_check seq <puzzle.json> <control>...`; `puzzle_check bypass <puzzle.json> <route> [<control>...]` (apply controls, then the route); `puzzle_check roundtrip <puzzle.json> <control>...`; `puzzle_check load <puzzle.json> <state.json>`. `seq`, `bypass` and `roundtrip` print a last line `state=<idle|partial|solved|bypassed> door_open=<0|1> opened_via=<none|puzzle|magic_key|pick_lock|break> wrong=<n> progress=<comma list>`.
  - `quest_check validate <quest.json> <strings.csv> <map.json>`; `quest_check stage <score>`; `quest_check line <strings.csv> <key> <stage>`; `quest_check fill <strings.csv> <key> <stage> <name=value>...`; `quest_check run <quest.json> <strings.csv> <map.json> <event>...` (events: `offer@<stage>`, `accept`, `decline`, `arrive@<node>[:present|gone]`, `report@<node>`, `char=<id>`, `stage=<n>`; prints one line per event and a final `state=<...>`; `stage=<n>` prints nothing, see below); `quest_check reward <seed|roll=<0..1>>`.

- Expected values come from the content files and the GDD. "TBD, not testable" means the GDD or content says TBD; no number is invented and the check cannot fail.
- **`stage=<n>` event (PROPOSAL for the Software Engineer; v2).** `quest_check run ... stage=<n>` (n an integer -2..2) sets the current standing of the active character before the next event; it changes no quest state and prints no line. `offer@<s>` also sets the standing to s. Every later `accept`, `decline`, `report@` and reward uses the current standing of the active character to pick the wording (cold for -2..0, warm for 1..2, as the CSV states). Standing is held per character (`char=<id>` switches it). Initial standing is 0. `n` outside -2..2 or non-integer: exit 1, `FAIL STAGE_RANGE`. If changed, record the change and reason.
