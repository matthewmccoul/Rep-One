## 4. Implement the scan and gap detection

A small scope file can tell the agent which GDD features belong to the run. Give the scanner the actual design text it needs to verify each requirement. For each requirement, output a status such as `implemented`, `partial`, `missing`, or `blocked`. Include evidence for that status, such as a source path and symbol, a known Blueprint or map reference, an integration path, or a specific failed runtime check. A file with a matching name is only a lead. Look for the behavior, where it is called in the game, and whether the required tests or checks pass. Scan the project the way a new developer would. Start with its README and source layout. Inspect the existing implementation before proposing new classes or systems. ## 5. Implement and use priority scoring

For missing or partial requirements, distinguish candidates whose dependencies are ready from candidates that are blocked. Score the ready candidates on a common scale. Let the runner pick the highest score and use a stable tiebreaker, such as requirement ID. Log every relevant candidate, its inputs and score, the selected requirement, and a plain-language reason. Where there is a dependency, log which feature is waiting and what will unblock it.

One possible rubric uses integer scores from 0 to 3. Change the weights if the project has a better documented rubric.

| Input | Meaning of a high score | Sample weight |
|---|---|---|
| Impact | The feature materially improves the current playable milestone. | 3 |
| Urgency | The feature is needed to test or complete the current milestone. | 2 |
| Unblocks work | The feature enables other in-scope requirements. | 1 |

For these weights, `priority_score()` can return `3 * impact + 2 * urgency + unblocks`. An eligible core interaction with scores of 3, 3, and 2 would receive 17. An eligible secondary feature scored 2, 1, and 0 would receive 8. These figures are examples. The evidence and scores in the submission should come from the actual run. If the model proposes the input ratings, require a reason linked to GDD and codebase evidence, then compute and sort by the score in code.

Joshua suggests ranking actions by impact, urgency, and expected value. His dungeon-crawler example changes the order based on which systems are already present and which dependencies are blocking play. His Q&A also suggests a simple numerical rubric that the developer reviews. See Class 7 at 6:46–7:33, 17:32–23:44, and 1:05:23–1:08:12.

## 6. Implement one change at a time and rescan

Give the implementation stage the winning requirement, its GDD source, evidence of the gap, relevant paths, and observable acceptance criteria. Have it make real writes in the game project, either by using authorized Claude Code editing tools or by returning a patch that the runner validates and applies. A change summary should identify the files the agent touched and how the feature connects to the running game.

Treat one implementation step as a coherent patch for one chosen gap. A patch may legitimately touch several files. Once the patch is written, run the relevant checks and immediately rescan the refreshed project tree. Score the remaining work from that new evidence, then continue with the next eligible gap. A build or playtest failure keeps the affected requirement open. Record the failure and give the next pass the specific error and the files the error concerns.

The runner's sequence should be visible in the implementation and the run log:

```text
Read the scoped GDD requirements
Scan the real project
Repeat while required gaps remain
    Score the eligible gaps and choose one
    Apply the agent's implementation
    Run the applicable build or behavior checks
    Rescan the updated code and record the result
Report success once all scoped requirements pass
```

Distinguish successful completion from a blocked or failed run. If a required dependency, permission, or tool is unavailable, or a retry produces no change, report the specific blocker and leave that requirement open. A small retry or iteration limit can stop a stalled run. Mark the goal complete only when the current evidence satisfies its acceptance criteria.

Use a short persistent run log, reusing the existing ledger or a simple Markdown blackboard if present. At minimum, capture the starting scan, score and rationale, selected gap, changed files, build or behavior check, updated scan, and final result. Keep an agent diff or a local commit reference so the grader can trace what actually changed. Joshua recommends defining done explicitly and keeping a lightweight record of state and decisions.
